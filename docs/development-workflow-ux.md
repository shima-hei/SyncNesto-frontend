# 要件から設計・テストへの作業導線

2026-10-14。チームのメンバーが自分で「何を書くか」「次に何をするか」「レビューのどこを直すか」を判断できることを目的とする。

## 操作の流れ

1. 要件書は名前と目的から作成し、保存すると「要件を書く・整理する」を開く。新規コードは空欄ならFrontendで `REQ-` + UUIDの先頭8文字を付与し、既存の必須API契約を維持する。コード・承認情報などは必要なときだけ展開する。
2. セクションを選んで要件名・内容・受け入れ条件を書く。「保存して続けて作成」で配置・分類・担当を引き継ぎ、本文を空にして次の要件へ進む。未確定の内容は既存の相談機能へつなぐ。
3. 要件の「設計・タスク・テスト」から画面設計書・API設計書を作成する。Projectナビの「画面・API設計」から全体も確認できる。
4. 設計書は名前と目的から下書きを作る。APIはmethod/path・認証認可・入出力・成功/エラー、画面は利用者・項目/規則・操作/遷移・状態を専用欄で具体化する。
5. 保存後の「関連」で要件・タスク・テスト項目・参考文書・他の設計書を検索して結び付ける。画面↔APIもここで管理し、参照先にも逆引きを表示する。
6. 確認依頼を出し、レビュー担当は各項目の「指摘」から1件ずつ投稿する。作成担当は指摘先へ移動し「この箇所を修正」で該当欄を開く。並べ替えても同じ項目へ戻り、内容変更や削除は警告する。
7. 修正後に指摘を解決し、権限のある担当者が承認する。未解決があれば承認できず、承認後に本文を変更すると下書きへ戻る。過去の内容は版履歴から確認する。

## 状態保持と入力保護

- 要件・タスク・文書・設計書の検索/ページ等をURLへ保持する。要件書はtab/sectionId/selectedRequirement/reviewTargetも保持する。一覧由来の詳細・編集は同じProjectの一覧URLにだけ戻れる。
- `returnTo` は外部URL・別Project・別詳細への遷移を拒否する。タスクの表、要件一覧と選択要件の導線に適用。ボード/ガントの全カードへは広げていない。
- 設計書の下書きは既存useFormDraftを利用する。通常は端末ローカル、匿名デモは既存のメモリ保存方針。端末をまたぐ共同下書きにはしない。
- 本文409時は項目UUIDを使った3方向比較。別々の編集は結合し、同じ欄の編集・削除対編集は比較画面で選ぶ。既存の要件書/要件の下書きと409処理を維持する。
- 要件プレビューは100件ずつ段階読込し、読込済み/全件数と続きの操作を表示する。全件未読込時はプレビュー文字位置に基づく指摘を無効にし、未読込の内容を削除済みと誤判定しない。
- 保存・状態更新・関連解除のエラーを表示し、競合時は最新情報を再取得する。編集不能な利用者には作成・編集操作を出さず、APIでも拒否する。

## 共通UI

既存の色・余白・shadcnコンポーネントを使用する。項目名にラベル、例、必須/任意を付ける。空の要件一覧は最初の1件と相談の入口を表示し、テスト設計は「操作と期待結果→必要ならパターン」という順序を案内する。一般文書・テスト項目にも関連設計書を表示する。

詳細な権限・上限・HTTP契約・migration順はBackend `docs/frontend-specifications-api.md`、生成型はOrvalを正とする。MCP既存ツール、通常ログインのDB、MFA・匿名デモの認証方針、審査用データは変更しない。新設計書のMCP操作、OpenAPI/Figma同期、設計書出力、同時編集、承認者の多段階割当は後続候補。
