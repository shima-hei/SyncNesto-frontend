# メールによるログイン情報の変更

本人のログイン情報は全組織で共有する。アカウント画面と組織管理画面からは変更用メールを送るだけにし、メールを受け取った本人が公開画面で操作する。

## 画面と承認

- `/forgot-password`: 未ログインでも登録先メールへパスワード再設定を申請できる。登録有無を判別できる表示をしない。
- `/reset-password#token=...`: 新しいパスワードを二重入力し、設定ボタンから確定する。12〜128文字。完了後は自動ログインしない。
- `/confirm-email-change#token=...`: 現在のメールで変更を承認し、次に変更先へ届いた別リンクでメールの受信を確認する。リンクを開いただけでは変更を実行しない。
- `/account`: 共通プロフィールは名前だけを直接更新する。パスワードは登録先へ再設定メールを送り、メール変更は現在のアドレスへ承認メールを送る。
- `/organization`: 所属編集画面に再設定メールとメール変更承認の申請を追加する。管理者が本人の新しいパスワードを指定する入力欄は設けない。

変更を確定すると対象Identityの既存セッションは失効する。メール変更は現在のアドレスでの承認、新しいアドレスでの確認を終えてから確定する。

## トークンとAPI

リンクのトークンはURL fragmentから読み、`history.replaceState` でURLから消してコンポーネント内だけに保持する。クエリ文字列・永続ストレージ・QueryClientのキーやmutation変数に保存しない。公開3画面には `no-referrer` を設定する。画面を再読込した場合はメール内のリンクを開き直す。

同じ確認画面の別リンクへ移動した場合もfragmentを読み直し、確認ステップとフォームを取り直す。前のステップの遅れた応答で新しいリンクを消去しない。

トークンの確認は `POST /auth/account-actions/inspect`、変更確定はそれぞれのPOSTへ送る。確認GETでは変更しない。API呼び出しはOrval生成関数と共通apiClientを使い、認証Cookieがある場合は既存CSRFヘッダーを付ける。Resendの秘密キーはFrontendに置かない。

公開認証画面はAuthProviderの未ログイン時のログイン誘導から除外する。保護された画面がブラウザーのBFcacheから復元された場合は再読込し、Server Guardと所属を取り直す。

組織内のRole・所属変更後は所属一覧も更新し、本人のRoleが変わった場合は組織の業務QueryClientを作り直す。
