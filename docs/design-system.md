# Syncnesto デザインシステム

Syncnesto はプロジェクト、要件、タスク、テストを長時間扱う業務アプリケーションである。情報を比較し、次の操作を迷わず選べることを優先する。shadcn/ui は操作部品の基盤として使い、画面構成と意味づけはこの文書に従う。

## 画面を作る前に

1. その画面で最初に判断すべき情報と、最も重要な操作を一つ決める。閲覧専用の画面に無理に強いボタンを置かない。
2. `パンくず → ページ見出し → 要約 → 画面内ナビゲーション → 絞り込み → 主内容` の順に検討する。不要な段は省く。
3. 一覧は原則として表にする。Card は独立した設定・プレビュー・要約など、独立した境界が必要な場合に限る。
4. 同じ情報や同じ行き先をページ内に繰り返さない。状態には必ず文字またはアイコンを添える。
5. モバイル幅、キーボード操作、ライト・ダーク両テーマ、空・読込・エラー状態を確認する。

## 基本要素

| 要素             | 基準                                     | 用途                                                       |
| ---------------- | ---------------------------------------- | ---------------------------------------------------------- |
| ページタイトル   | `text-2xl font-semibold tracking-tight`  | 画面内で一つの `h1`                                        |
| セクション見出し | `text-base font-semibold`                | `h2`、必要なら下位に `h3`                                  |
| 本文・表         | `text-sm`                                | 長文は `leading-6`、適度な行長に制限                       |
| 項目ラベル       | `text-sm font-medium`                    | フォームや表の見出し                                       |
| 補足・メタ情報   | `text-xs text-muted-foreground`          | ID、日時、補足。主内容より弱くする                         |
| 余白             | 4 / 8 / 12 / 16 / 24 / 32px              | 同じ関係には同じ間隔を使う。`gap-*` を優先                 |
| 角丸             | 小〜中を用途別に使用                     | 操作部品の既存 variant を優先。大きな角丸を重ねない        |
| 境界             | `border-border` と `Separator`           | 表の行やセクションの分離に限定し、枠線だけで階層を作らない |
| 影               | 原則としてポップオーバー等の浮いた面のみ | 通常のセクションに装飾目的の影を付けない                   |

シェルの `ProtectedShell` がページ余白を持つ。配下の画面で同じ `p-4` / `p-6` を重ねない。ページ内の縦方向は原則 `gap-4`〜`gap-6` とし、関係の近い要素は `gap-1`〜`gap-3` にする。

## 色・状態

`app/globals.css` の `background`、`foreground`、`muted`、`primary`、`destructive`、`border`、`ring` と、既存の `--status-neutral/info/progress/warning/success/danger-{bg,fg,border}` を使う。画面固有の `bg-red-100` のような直接色指定を増やさない。同義の token を追加せず、既存の状態色で不足する意味が明らかなときだけ追加を検討する。

| 意味                 | 色の役割             | 併記する情報           |
| -------------------- | -------------------- | ---------------------- |
| 未実施・補足         | neutral / muted      | 状態名                 |
| 選択・情報           | info / primary       | 選択表示または状態名   |
| 実施中               | progress             | 「実施中」             |
| 注意・保留・期限超過 | warning              | 「保留」「期限超過」等 |
| 成功・完了           | success              | 「OK」「完了」等       |
| 失敗・削除           | danger / destructive | 「NG」「削除」等       |

状態は背景色だけで表さない。選択、設計変更の影響、実行結果など異なる概念に同じ印だけを使わない。本文文字は通常 4.5:1、大きい文字は 3:1 のコントラストを目安に実測する。キーボードフォーカスは `ring` または輪郭線で常に視認できるようにする。

## 操作部品

- Button: ページの主操作を原則一つだけ強調する。補助操作は `outline` / `ghost`、破壊的操作は `destructive` を使う。閲覧画面には主操作がなくてもよい。
- Navigation: 全体 Sidebar、プロジェクト内ナビ、画面内 Tabs の役割を分ける。現在位置を文字の強さと線などで示し、フォーカスも別に示す。パンくずとページタイトルの役割を混同しない。
- Table: 列見出しと行の対応を明確にし、主要な識別子から詳細に移動できるようにする。行全体をクリック可能にする場合は、行内操作のイベントを分離する。狭い画面では必要な列を優先し、横スクロールが必要なら分かるようにする。
- Card: 独立した情報単位だけに使う。Card 内に同じ強さの Card を並べない。状態の数値は枠なしの `dl` や区切り線でも示せる。
- Badge: 短い状態・カテゴリに限る。多数の状態の内訳を並べる場合は、重要な数字だけ要約するか、表で詳細を見せる。
- Form: shadcn の既存 Input / Select / Field 系と意味別 token を使い、ラベル・説明・エラーの位置を揃える。クリック対象には十分な高さを確保する。
- Dialog / Sheet / Dropdown / Tooltip: 既存部品を使用し、Title、フォーカス遷移、Escape、破壊的操作の明示を確認する。Tooltip だけに必須情報を置かない。
- Empty / Loading / Error / 権限なし: `components/shared/feedback/` の既存部品を優先する。何がないか、次に何ができるかを示す。読込骨格は実際の情報構造に近づける。

クリックできる範囲と hover / focus / selected / disabled 状態を一致させる。キーボードで到達できない hover 専用操作を置かない。

## テスト管理の密度

テスト項目・ケース・パターン・Issue・実行履歴は一画面で比較できる密度を優先する。スプレッドシート部分には通常の Card ルールを適用せず、グリッド、選択・編集状態、固定見出し、キーボード操作を優先する。周辺の見出しやダイアログは共通ルールに従う。

## 既存画面の調査と展開順

| 領域               | 現状                                                                         | 次の改善単位                                |
| ------------------ | ---------------------------------------------------------------------------- | ------------------------------------------- |
| プロジェクト概要   | 外側の余白と Card が重なり、下部リンクがプロジェクト内ナビと重複             | 第1段階で見出し、概要、指標、タスク表に整理 |
| 要件定義書         | 表は利用済み。見出しと作成操作が分かれている                                 | Page Header と操作配置を揃える              |
| タスク             | 表・ボード・ガントを利用済み。各表示の見出し・ツールバーを統一する余地がある | タブとフィルタの階層を確認                  |
| テスト設計書       | 編集グリッドと周辺 UI の密度が異なる                                         | グリッドの操作を維持して周辺 UI を整理      |
| テストケース・実行 | 表は利用済み。一部の状態色が画面内の直接指定                                 | 既存状態 token に揃え、状態と影響を別に表示 |
| 進捗・集計         | 数値ごとの小さな枠と状態色の直接指定が多い                                   | 重要な数字を一つの要約領域にまとめる        |

共通化は二画面以上で同じ使い方が確認できてから行う。候補は PageHeader、PageSection、Metric、StatusBadge、TableToolbar。既存の `SearchFilterBar`、`EmptyState`、`LoadingState`、`ConfirmDialog` を優先し、類似部品を増やさない。

## 第1段階のプロジェクト概要

Before: プロジェクトコードのみの見出し、概要 Card、タスク Card と小さな指標枠、重複したリンクボタン群。

After: プロジェクト名とコード、説明と期間、区切り線、タスクの主要指標、期限超過と直近期限の表。タスクの詳細への操作はセクション見出し、各タスクへの操作は表の行に置く。プロジェクト内の他機能へは既存ナビから移動する。

この画面で確認したパターンを次の画面に適用するときは、まず現状と用途を比較し、機械的に全画面へ同じ余白や表を適用しない。

## 第2段階の要件定義書・タスク一覧

両画面の見出しと主要操作は `PageHeader` に揃える。シェルとページで余白を重ねず、検索・フィルタは表の直前に配置する。タスク一覧では頻繁に使う条件を表示し、詳細条件は開閉できるようにする。詳細条件が有効な場合は、閉じていても件数を表示する。一括更新の操作欄は行を選択したときだけ表示する。

状態表示には共通の `StatusBadge` と既存の状態色 token を使う。機能ごとに状態値から意味別の tone を決め、表示部品に直接色を重複定義しない。要件定義書とタスクの表は、行全体の移動操作に加えて名称を通常のリンクとして提供し、別タブで開く操作やキーボード操作を可能にする。取得エラーは空の一覧として扱わず、再試行操作を表示する。

## 第3段階のテストケース・進捗

テストケースの行色と進捗内訳は `case-status.ts` で同じ状態定義を参照し、既存の状態色 token を用いる。「設計変更の影響」は実行状態と別の列・警告アイコンで示し、両方の状態を同時に読めるようにする。進捗の主要数値は一つの要約領域に置き、内訳からケース一覧へ移動できるようにする。取得エラーは空のケース一覧や NG なしと区別し、再試行を表示する。
